Unless an entry says otherwise, the recorded environment is Project Zomboid Build 42.20.x on a dedicated server with one connected test client.

| 2026-09-05 | 0.0.37 | Mixed single-pair and mass-combat stress test (24v24, 24v24 crawlers, 240v240) | Passed the single-pair posture matrix and reproduced the dormant-mob-member defect directly. Server-side profile transitions confirmed correct `STANDING_BITE`, `STANDING_STOMP`, and `CRAWLER_LUNGE` selection, plus a `STOMP`-to-`BITE` transition on one tracked pair consistent with a successful sitting get-up, the first such confirmation since the defect was recorded in SPIKE-004. Reopened [Issue #2](https://github.com/jonathanjacobs/pz-zombie-factions/issues/2), which had been closed on an earlier stress run that did not reproduce it. | [Issue #2](https://github.com/jonathanjacobs/pz-zombie-factions/issues/2) |
| 2026-09-05 | 0.0.38 | Dormant-mob-member fix validation | Passed. A follow-up run using the same mixed single-pair and mass-combat matrix recorded a periodic-sweep reactivation of a member that had held no target since joining its mob, three minutes after the last spawn and without player action (`reason=mob-active-recruit`) — a recovery the pre-fix code could not perform. A 480-zombie double spawn (240+240) reached full activation (`dormant=0`, `active=480`) within roughly ten seconds of landing. `dormant` climbed again late in the session (0 to 47 over the final two minutes), but `memberSelections` climbed into the hundreds over the same window, indicating active retry rather than the original non-retry defect; read as target scarcity in the tail of a mostly finished battle, not a recurrence. No Zombie Factions exception, zero profile rejections, 1,635 damage requests, 1,393 accepted. Closed [Issue #2](https://github.com/jonathanjacobs/pz-zombie-factions/issues/2). | [Issue #2](https://github.com/jonathanjacobs/pz-zombie-factions/issues/2) |
